Solution Pattern: Unified Workload Migration to OpenShift Virtualization

Architecture

The architecture migrates virtual machines from a legacy hypervisor into Red Hat OpenShift Virtualization, where KubeVirt runs each VM inside a pod. The Migration Toolkit for Virtualization orchestrates the move; Multus and Kubernetes storage complete the landing zone.

1. Common Challenges

  • Hypervisor lock-in: proprietary formats, tooling and licensing make the current platform expensive to keep and hard to leave.

  • Two operational worlds: VMs and containers are managed by different teams, tools and processes.

  • Networking and storage gaps: VLANs, multiple NICs and persistent disks must map cleanly onto Kubernetes concepts.

  • Migration risk: cutover windows, data consistency and rollback plans decide whether the project is trusted.

2. Technology Stack

  • Red Hat supported products

    • Red Hat OpenShift

    • Red Hat OpenShift Virtualization (KubeVirt)

    • Migration Toolkit for Virtualization (MTV / Forklift)

    • Red Hat OpenShift Data Foundation

  • Other open source products:

    • KubeVirt

    • Multus CNI

    • Containerized Data Importer (CDI)

    • Kubernetes CSI storage

3. An in-depth look at the solution’s architecture

3.1. Source and target

The source is a traditional hypervisor estate (for example VMware vSphere). The target is an OpenShift cluster — bare metal for performance-sensitive VMs, or any certified infrastructure — with the OpenShift Virtualization operator installed and a default storage class suitable for virtual disks.

3.2. Migration flow

  1. MTV connects to the source provider and inventories VMs, networks and datastores.

  2. A migration plan maps source networks to Multus NetworkAttachmentDefinitions and source datastores to a storage class.

  3. Disks are copied with CDI (warm migration pre-copies data while the VM keeps running).

  4. At cutover, the VM is shut down on the source, the final delta is synced, and a KubeVirt VirtualMachine is started on OpenShift.

3.3. Networking and storage

VMs keep their identity: Multus attaches them to the same VLANs they used before, while pod networking remains available for management and metrics. Persistent disks become PersistentVolumeClaims; CDI imports golden images so new VMs can be cloned in seconds.

3.4. Day-2 operations

Live migration, snapshots, console and serial access, monitoring through OpenShift’s built-in stack, and backup with the platform’s standard tooling — all from the same console and API used for containers.

4. More about the technology stack

OpenShift Virtualization is based on KubeVirt, the CNCF project that extends Kubernetes with VirtualMachine resources. Because a VM is a Kubernetes object, everything in the ecosystem — GitOps controllers, policy engines, service meshes and observability stacks — can see it and manage it. MTV is based on the open source Forklift project and supports migrations from VMware vSphere, Red Hat Virtualization, OpenStack and OVA files.
